# Scrooge Alert - Development Context

## Project Overview
This project is an automated Python application designed to monitor prices through checked-in product-page and classified-listing plugins and send push notifications when offers drop below user-defined target thresholds.

- **Main Technologies:** Python 3, `apprise` (for versatile push notifications), optional plugin-private transports/parsers such as `tls_client`, and systemd (for automated background scheduling on Linux).
- **Architecture:** The application features a modular, plugin-based architecture residing in `src/core/`. The entrypoint is `main.py`, which delegates to specialized modules:
  - **Scrapers (`scrapers/`)**: `api.py` is the stable descriptor contract; `domain.py` owns shared URL parsing and canonicalization; `framework/` owns discovery, compilation, configuration, settings, clients, and state; `support/` holds opt-in HTTP and pricing helpers; `tooling/` holds contributor CLIs; and checked-in adapters live under `plugins/`. Production plugin packages require import-light `__init__.py` and `plugin.py`, conventional `client.py:Client`, `README.md`, and `config.example.json`; custom item fields/settings and private `requirements.txt` are optional. `core.scrapers.api` is the only descriptor import surface (`ScraperPlugin`, `ItemField[T]`, re-exported `SettingSpec[T]`, `TrackedItem`, `ScraperClient`, result/offer types, and modeled exceptions). Descriptors declare a parsed-URL predicate, host-only domains, fields, settings, and canonical default interval. The framework derives the client binding.
    - **Framework data contracts**: The framework decodes immutable `TrackedItem` values and owns strict schema-versioned JSON configuration plus versioned atomic state persistence. Explicit item IDs are the only state keys; queries are preserved and fragments removed. `PriceResult`, `ListingResult`, and `Offer` validate and normalize themselves, and listing offer iterables are snapshotted to tuples.
    - **Catalog and clients (`scrapers/framework/catalog.py`, `compiler.py`, `clients.py`)**: Immutable `PluginCatalog` handles atomic discovery while `compile_plugin` owns key/codec/canonical-default validation without mutating declarations. One-shot `ClientLoader` constructs conventional clients with explicit resolved settings; `TargetRunner` owns one client per target and closes it in that target's `finally` block. URL canonicalization, domain matching, and descriptor matching are one compiled-plugin operation. Multiple adapters may support the same domain.
    - **Persistence (`scrapers/framework/configuration.py`, `state.py`)**: `TargetConfigLoader` reads each config once, validates unknown keys, decodes valid rows, and reports invalid rows structurally. `JsonStateRepository` treats missing state as empty, rejects malformed existing state without overwriting it, and saves only pending price/check and successful-alert-history changes under the target lock. Schema-v2 alert history distinguishes one continuous single-price deal episode from canonical per-offer listing URLs.
  - **Application layer (`application/`)**: `ScrapingOrchestrator` coordinates target selection, configuration failures, reporting, interruption, summaries, and final exit status. `TargetRunner` owns one target's locked repository/client lifecycle and one state commit; `items.py`, `pacing.py`, `retry.py`, and `results.py` separately own sequential item execution, request pacing, error policy, and successful-result evaluation/state staging. `contracts.py` contains presentation-neutral run contracts, `preflight.py` owns configuration-only target loading and background notification gating, and `reporting.py` contains `SilentRunReporter`.
  - **Notifications (`notifications/`)**: `contracts.py` is the application-facing delivery protocol, `configuration.py` validates and classifies the notification section once, `templates.py` builds messages without transport access, and `apprise.py` registers already-valid URLs and delivers through Apprise.
  - **General configuration (`general/`)**: One immutable, read-once load of `config/general.json` isolates notification and reminder-setting failures and carries advisory permission health without exposing credentials. Reminder scheduling lives in `reminder.py`/`reminder_schedule.py`; schema-versioned `state/general.json` persistence lives in `reminder_state.py`.
  - **Infrastructure (`infrastructure/`)**: Technical adapters for locking, logging, atomic JSON/timestamp persistence, process signals, read-only systemd inspection, and remote update checks. Infrastructure does not import application or TUI modules.
  - **Terminal UI (`tui/`)**: Presentation-only builders for Configuration Check, ping, and status panels; service-exit verdicts; shared panel primitives; and the Rich `InteractiveRunReporter`. Presentation helpers receive collected inputs and perform no configuration, filesystem, network, or systemd access.
  - **CLI Tools (`main.py`, `ping.py`, `status.py`)**: Root-level entry points collect data and compose the application, infrastructure, and TUI layers. `status.py` performs its own read-only state inspection after successful target-configuration loading.
  User configuration is externalized to strict schema-versioned `config/<target>.json` files and `config/general.json`; the latter is the sole source of project-wide notification URLs and reminder settings. Runtime and ordinary installation are read-only; explicit migration tooling invoked by updates may atomically migrate configuration and machine state. Machine data remains schema-versioned in ignored `state/<target>.json` and `state/general.json`, with aware RFC 3339 UTC `Z` timestamps.

## Building and Running
The application is primarily intended for automated background execution but provides wrapper scripts for easy management and manual testing. All execution goes through the venv (`./venv/bin/python3`); the wrapper scripts handle this for you.

A test suite lives under `tests/` (`tests/unit/`, `tests/integration/`, target-owned `tests/plugins/`, the terminal-UI snapshot suite in `tests/ui/`, and `tests/shell/`). It runs under **pytest**, configured in the repo-root `pyproject.toml`. Coverage is report-only: no coverage percentage may fail a local or CI test run, and `--cov-fail-under`/`fail_under` thresholds must not be introduced. Use `./scripts/dev/setup.sh` to install core, development, and discovered plugin dependencies without systemd side effects, then run `./venv/bin/python3 -m pytest`. CI runs Python 3.10 through 3.14, an isolated dependency check for every plugin, **shellcheck**, and `basedpyright src`. Shared test infrastructure uses injected catalogs rather than mutating discovery globals. **User-facing run wording lives in `core/messages.py`**; UI changes regenerate with `UPDATE_SNAPSHOTS=1`.

Agents must never create commits or push changes. They leave all implementation
work uncommitted for the user to review and control. Before reporting a code
change complete, an agent must run `./scripts/dev/check.sh` from the repository root.
It is the required non-mutating local CI gate (Ruff lint/format check,
basedpyright, shellcheck, dependency validation, and the full test suite). Rerun
it after every subsequent file change. If a check cannot run or fails, report
that explicitly and do not claim the work is complete or CI-ready. Passing
pytest alone is not sufficient. The versioned pre-push hook is enabled
automatically by `./scripts/dev/setup.sh` for user-initiated pushes.

- **Installation:** Execute `./install.sh`. This creates a project-owned venv, installs core dependencies plus each selected plugin's catalog-computed colocated `requirements.txt`, and generates one systemd user timer+service pair per plugin. The effective cadence is the valid `settings.execution_interval` or the plugin definition's canonical `default_interval`. The framework exclusively renders `OnCalendar`, explicit `Unit=<plugin>-scraper.service`, `RandomizedDelaySec=180s`, and `Persistent=true`; plugins cannot inject timer directives. A target with a structurally invalid config is reported and skipped while other selected targets are provisioned, its existing units are left unchanged, and the command exits `15`. A missing private dependency fails that target with actionable `PluginDependencyError` guidance.
- **Automated Execution:** Handled automatically by the per-plugin systemd timers (`<plugin>-scraper.timer`, e.g. `skroutz-scraper.timer`).
- **Service Management:** Use `./scripts/disable.sh` to temporarily stop and disable the background timer(s), `./scripts/enable.sh` to resume them, and `./scripts/stop.sh` to forcefully kill a running execution. With no flag these act on **all** plugins; pass `--<plugin>` (e.g. `./scripts/disable.sh --skroutz`) to target a single store. `./scripts/schedule.sh` re-applies each scraper's configured `execution_interval` to its installed timer as one staged transaction (atomically replaces each timer, then performs one `daemon-reload`; active timers are restarted and verified); run it after editing that setting — a missing config or an unsupported value is reported and that timer left unchanged. A structurally invalid config is isolated to its target: multi-target install/schedule/update operations continue for healthy targets, preserve that target's existing units, and exit `15`. Systemd queries/actions fail closed: only known absent/inactive states are benign, every action verifies its postcondition, multi-target commands report all independent failures, and update/uninstall perform no destructive phase unless every scraper was safely stopped. Rollback restores prior regular files or absence and timer state; incomplete rollback retains private recovery artifacts. Shared target selection uses explicit registered, installed-and-registered timer, installed service, and installed union policies so removed upstream plugins remain tear-downable while typos fail. `./update.sh` preserves the user's installed plugin selection and advances `origin/main` only by verified fast-forward. All shell scripts are POSIX `sh` and use two independent TSV snapshots: a config-independent plugin catalog for identity/static paths and a per-target schedule report that can carry isolated configuration errors.
- **Manual Execution:** Execute `./scripts/run.sh` to run the scraper interactively and view output logs in the terminal. Flags: `--quiet` (no console output) and one dynamically generated flag per registered plugin (e.g. `--skroutz`) to run only that scraper. The `--ping` and `--status` flags must be used alone.
- **Direct Invocation:** `./venv/bin/python3 src/core/main.py` — the entry scripts (`main.py`, `status.py`, `ping.py`) insert `src/` (the parent of the `core` package) into `sys.path`, and all intra-project imports are absolute from that package (e.g. `from core.scrapers.framework.catalog import ...`), never implicitly relative (`from scrapers...`) or rooted at `src` (`from src.core...`).
- **Help Message:** Execute `./scripts/run.sh --help` to print the help message and view all available script arguments.
- **Testing Notifications:** Run `./scripts/run.sh --ping` to send a test payload and verify the Apprise URLs in `config/general.json`.
- **Health Checks:** Run `./scripts/run.sh --status` to perform a comprehensive health check. This validates the configuration (tracked items, notification endpoints, general settings, and advisory general-config permissions), checks for available script updates, and verifies the status of the background systemd service and timer. The shared **Configuration Check** panel carries only the global checks; each scraper's **target-configuration health** (a `Config` row: `N items loaded` / `M misconfigured` / `Failed`) is surfaced per-scraper, at the top of that scraper's **Service Status** panel alongside its settings section — built by the shared `config_check.config_view`/`add_config_row` (the interactive run shows the same `Config` row atop each **Scraping** panel). It footnotes per-scraper **settings issues** — a live timer whose schedule has drifted from the configured `execution_interval` (pointing at `./scripts/schedule.sh`) and an out-of-range `log_retention_days` — and surfaces **orphaned units** — installed `*-scraper.{timer,service}` units whose plugin is no longer registered (removed/renamed upstream) — each in its own red panel with the `./scripts/uninstall.sh --<plugin>` command to remove them, since they never run and are otherwise invisible to the per-plugin status loop.
- **Uninstallation:** Execute `./scripts/uninstall.sh` to cleanly stop and disable the systemd services and remove the virtual environment (user data is preserved). It removes every installed `*-scraper.{service,timer}` unit (robust to plugins deleted from the source tree). Pass `--<plugin>` (e.g. `./scripts/uninstall.sh --skroutz`) to drop only that plugin's units while keeping the venv and other plugins.
- **Exit Codes:** The script utilizes specific exit codes to indicate failure states when running as a service (these can be easily viewed using the `--status` flag):
  - **`15`**: Indicates an issue with a target's tracked-items configuration, e.g. `config/skroutz.json` (file missing, wrong permissions, invalid JSON, or an invalid schema). Such a scraper is **skipped individually** — other selected scrapers still run or are provisioned — and the command finishes with this code if any target's config failed to load. For install/schedule/update, the failed target's existing units are left unchanged.
  - **`16`**: Indicates unusable notification configuration in `config/general.json`.
  - **`17`**: Indicates the scraper was blocked by the server due to rate limits.
  - **`18`**: Indicates that a parser or unexpected scraper fault exhausted all retries. Modeled remote/server errors remain successful and surface through error/stale notifications.
  - **`19`**: Indicates that machine state could not be loaded or persisted through the atomic state path.
  - **`20`**: Indicates that at least one configured notification failed to deliver. `--status` presents this as a yellow notification warning; scraping continues.
  - **`21`**: Indicates that a selected scraper could not start because its private plugin dependencies are missing.
  - **`42`**: Indicates that a specific scraper target did not start because another instance of it is already running (file lock timeout).
  - **`130`**: Indicates that the script was interrupted (e.g., via Ctrl+C or system termination).

## Development Conventions
- **Scraping Practices & Rate Limiting:** The framework intentionally paces requests using a base delay (20s) plus randomized jitter (1-5s) between item checks to reduce pressure on monitored sites. Concurrency is avoided. Do not "optimize" this away.
- **Data Integrity:** Runtime never writes `config/*.json`. Scraper machine updates go through `JsonStateRepository` under the existing per-target lock; reminder updates go through `ReminderStateRepository` under the reminder lock. Both use the atomic writer and preserve malformed existing state.
- **Managed-path symlink policy:** Scrooge Alert creates a real root `venv/` directory and regular canonical systemd unit files. The enablement symlinks that systemd creates below directories such as `timers.target.wants/` are expected systemd-owned entries, not project-managed destinations. Symlinks placed at project-managed destinations are unsupported: mutating commands reject them before changing packages, units, or timer state, while teardown remains link-aware so uninstall can remove a unit entry without following its target. JSON migration inputs must likewise be regular files because migration replaces them atomically. Keep these small fail-closed boundary checks, but do not add symlink normalization, target-following writes, or exact-representation preservation behavior.
- **Error Handling & Logging:** When running silently in the background, exceptions are caught and logged to the relevant `errors.txt` — `logs/<target>/errors.txt` for a specific scraper (e.g. `logs/skroutz/errors.txt`), falling back to the root `logs/errors.txt` for top-level crashes with no target context. Background stdout is written to `logs/<target>/output.log`, which rotates daily at midnight UTC and keeps the scraper's configured `log_retention_days` of files (default 7; the surplus is pruned at the next rotation). Timestamps in these logs are recorded in UTC. If critical errors occur (like repeated scraping failures or a total crash), the script utilizes the Apprise notifier to alert the user of the failure.
- **Code Style:** Adding a store is additive: use `./scripts/dev/plugin-create.sh` and change only the new source and test packages. Targets and declaration keys are snake_case; domains are normalized hostnames/IPs only and may overlap across adapters. Export conventional `Client`, declare a parsed-URL predicate and canonical interval, and add only optional custom fields/settings/dependencies. Compilation validates codecs, already-canonical defaults, reserved keys, control-character safety, URL matcher behavior, and runtime Python files; the contributor verifier owns documentation, tests, examples, package isolation, and import-effect checks. Runtime results validate nonblank currency/title, finite non-negative non-boolean prices, immutable snapshotted offers, and absolute HTTP(S) offer URLs. Invalid construction follows parse retries and never persists or alerts.
