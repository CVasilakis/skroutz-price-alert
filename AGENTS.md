# Scrooge Alert - Development Context

## Project Overview
This project is an automated Python application designed to monitor prices through checked-in product-page and classified-listing plugins and send push notifications when offers drop below user-defined target thresholds.

- **Main Technologies:** Python 3, `apprise` (for versatile push notifications), optional plugin-private transports/parsers such as `tls_client`, and systemd (for automated background scheduling on Linux).
- **Architecture:** The application features a modular, plugin-based architecture residing in `src/core/`. The scraping entrypoint is `run.py`, which delegates to specialized modules:
  - **Scrapers (`scrapers/`)**: `api.py` is the stable descriptor contract; `domain.py` owns shared URL parsing and canonicalization; `framework/` owns discovery, compilation, configuration, settings, clients, and state; `support/` holds opt-in HTTP and pricing helpers; `tooling/` holds contributor CLIs; and checked-in adapters live under `plugins/`. Production plugin packages require import-light `__init__.py` and `plugin.py`, conventional `client.py:Client`, `README.md`, and `config.example.json`; custom item fields/settings and private `requirements.txt` are optional. `core.scrapers.api` is the only descriptor import surface (`ScraperPlugin`, `ItemField[T]`, re-exported `SettingSpec[T]`, `TrackedItem`, `ScraperClient`, result/offer types, and modeled exceptions). Descriptors declare a parsed-URL predicate, host-only domains, fields, settings, and canonical default interval. The framework derives the client binding.
    - **Framework data contracts**: The framework decodes immutable `TrackedItem` values and owns strict schema-versioned JSON configuration plus versioned atomic state persistence. Explicit item IDs are the only state keys; queries are preserved and fragments removed. `PriceResult`, `ListingResult`, and `Offer` validate and normalize themselves, and listing offer iterables are snapshotted to tuples.
    - **Catalog and clients (`scrapers/framework/catalog.py`, `compiler.py`, `clients.py`)**: Immutable `PluginCatalog` handles atomic discovery while `compile_plugin` owns key/codec/canonical-default validation without mutating declarations. One-shot `ClientLoader` constructs conventional clients with explicit resolved settings; `TargetRunner` owns one client per target and closes it in that target's `finally` block. URL canonicalization, domain matching, and descriptor matching are one compiled-plugin operation. Multiple adapters may support the same domain.
    - **Persistence (`scrapers/framework/configuration.py`, `state.py`)**: `TargetConfigLoader` reads each config once, validates unknown keys, decodes valid rows, and reports invalid rows structurally. `JsonStateRepository` treats missing state as empty, rejects malformed existing state without overwriting it, and saves only pending price/check and successful-alert-history changes under the target lock. Schema-v1 alert history distinguishes one continuous single-price deal episode from canonical per-offer listing URLs.
  - **Application layer (`application/`)**: `ScrapingOrchestrator` coordinates target selection, configuration failures, reporting, interruption, summaries, and final exit status. `TargetRunner` owns one target's locked repository/client lifecycle and one state commit; `items.py`, `pacing.py`, `retry.py`, and `results.py` separately own sequential item execution, request pacing, error policy, and successful-result evaluation/state staging. `contracts.py` contains presentation-neutral run contracts, `preflight.py` owns configuration-only target loading and background notification gating, and `reporting.py` contains `SilentRunReporter`.
  - **Notifications (`notifications/`)**: `contracts.py` is the application-facing delivery protocol, `configuration.py` validates and classifies the notification section once, `templates.py` builds messages without transport access, and `apprise.py` registers already-valid URLs and delivers through Apprise.
  - **General configuration (`general/`)**: One immutable, read-once load of `config/general.json` isolates notification and reminder-setting failures and carries advisory permission health without exposing credentials. Reminder scheduling lives in `reminder.py`/`reminder_schedule.py`; schema-versioned `state/general.json` persistence lives in `reminder_state.py`.
  - **Infrastructure (`infrastructure/`)**: Technical adapters for locking, logging, atomic JSON/timestamp persistence, process signals, read-only systemd inspection, and remote update checks. Infrastructure does not import application or TUI modules.
  - **Terminal UI (`tui/`)**: Presentation-only builders for Configuration Check, ping, and status panels; service-exit verdicts; shared panel primitives; and the Rich `InteractiveRunReporter`. Presentation helpers receive collected inputs and perform no configuration, filesystem, network, or systemd access.
  - **CLI Tools (`run.py`, `ping.py`, `status.py`)**: Independent root-level entry points collect data and compose the application, infrastructure, and TUI layers. `status.py` performs its own read-only state inspection after successful target-configuration loading.
  User configuration is externalized to strict schema-versioned `config/<target>.json` files and `config/general.json`; the latter is the sole source of project-wide notification URLs and reminder settings. Runtime and ordinary installation are read-only; explicit migration tooling invoked by updates may atomically migrate configuration and machine state. Machine data remains schema-versioned in ignored `state/<target>.json` and `state/general.json`, with aware RFC 3339 UTC `Z` timestamps. Cooperative locks live in `state/locks/`: `<target>.lock` for every current or future plugin plus the reserved framework names `reminder.lock` and `migration.lock`.

## Building and Running
The application is primarily intended for automated background execution but provides wrapper scripts for easy management and manual testing. All execution goes through the venv (`./venv/bin/python3`); the wrapper scripts handle this for you.

A test suite lives under `tests/` (`tests/unit/`, `tests/integration/`, target-owned `tests/plugins/`, the terminal-UI snapshot suite in `tests/ui/`, and `tests/shell/`). It runs under **pytest**, configured in the repo-root `pyproject.toml`. Coverage is report-only: no coverage percentage may fail a local or CI test run, and `--cov-fail-under`/`fail_under` thresholds must not be introduced. Use `./scripts/dev/setup.sh --debug` to install core, development, and discovered plugin dependencies without systemd side effects, then run `./venv/bin/python3 -m pytest`. CI runs Python 3.10 through 3.14, an isolated dependency check for every plugin, **shellcheck**, and `basedpyright src`. Shared test infrastructure uses injected catalogs rather than mutating discovery globals. **User-facing run wording lives in `core/messages.py`**; UI changes regenerate with `UPDATE_SNAPSHOTS=1`.

Agents must never create commits or push changes. They leave all implementation work uncommitted for the user to review and control. Before reporting a code change complete, an agent must run `./scripts/dev/check.sh --debug` from the repository root. It is the required non-mutating local CI gate (Ruff lint/format check, basedpyright, shellcheck, dependency validation, and the full test suite). Rerun it after every subsequent file change. If a check cannot run or fails, report that explicitly and do not claim the work is complete or CI-ready. Passing pytest alone is not sufficient. The versioned pre-push hook is enabled automatically by `./scripts/dev/setup.sh` for user-initiated pushes.

Whenever an agent invokes a project shell entry point that supports `--debug`, it must pass that flag so the complete underlying command output is captured. This applies to installation, updates, migrations, service-management commands, and every script under `scripts/dev/`. The runtime wrappers (`scripts/run.sh`, `scripts/ping.sh`, and `scripts/status.sh`) deliberately have no shell-level debug mode because their Python entry points own their TUI, runtime diagnostics, and logging.

- **Installation:** Execute `./scrooge-alert install`. This creates a project-owned venv, installs core dependencies plus each selected plugin's catalog-computed colocated `requirements.txt`, and generates one systemd user timer+service pair per plugin. The effective cadence is the valid `settings.execution_interval` or the plugin definition's canonical `default_interval`. The framework exclusively renders `OnCalendar`, explicit `Unit=<plugin>-scraper.service`, `RandomizedDelaySec=180s`, and `Persistent=true`; plugins cannot inject timer directives. A target with a structurally invalid config is reported and skipped while other selected targets are provisioned, its existing units are left unchanged, and the command exits `15`. A missing private dependency fails that target with actionable `PluginDependencyError` guidance.
- **Automated Execution:** Handled automatically by the per-plugin systemd timers (`<plugin>-scraper.timer`, e.g. `skroutz-scraper.timer`). Each timer invokes exactly one scraper target, so an unattended run is always single-target; the exit-status policy relies on this (see `42` below). Multi-target runs happen only when a user invokes them manually.
- **Repository-local Command:** `./scrooge-alert` is the canonical user interface and dispatches to POSIX scripts under `scripts/`. It installs no launcher or shell completion and does not modify `PATH` or shell profiles. Use `disable`, `enable`, `stop`, and `schedule` subcommands for service management; `update` preserves the installed plugin selection and advances `origin/main` only by verified fast-forward. Systemd continues to execute `scripts/run.sh` directly. All shell scripts use two independent TSV snapshots: a config-independent plugin catalog for identity/static paths and a per-target schedule report that can carry isolated configuration errors.
- **Manual Execution:** Execute `./scrooge-alert run` to run the scraper interactively. It accepts `--quiet` and dynamic `--<plugin>` target flags. Use `./scrooge-alert ping` and `./scrooge-alert status` for notification and health checks. The internal `scripts/run.sh` interface remains the systemd and recovery entry point.
- **Direct Invocation:** `./venv/bin/python3 src/core/run.py` — the entry scripts (`run.py`, `status.py`, `ping.py`) insert `src/` (the parent of the `core` package) into `sys.path`, and all intra-project imports are absolute from that package (e.g. `from core.scrapers.framework.catalog import ...`), never implicitly relative (`from scrapers...`) or rooted at `src` (`from src.core...`).
- **Help Message:** Execute `./scrooge-alert --help` for commands or `./scrooge-alert <command> --help` for command-specific dynamic options.
- **Testing Notifications:** Run `./scrooge-alert ping` to send a test payload and verify the Apprise URLs in `config/general.json`.
- **Health Checks:** Run `./scrooge-alert status` to perform a comprehensive health check. This validates the configuration (tracked items, notification endpoints, general settings, and advisory general-config permissions), checks for available script updates, reports whether systemd **user lingering** is enabled, and verifies the status of the background systemd service and timer. The lingering row is advisory and never changes an exit status: `install.sh` enables lingering best-effort, so `status` only re-reports it, and a host without `loginctl` omits the row rather than warning. The update check compares the checkout against remote `HEAD` only on the `main` release branch; any other named branch is reported as such instead, since `update` advances `main` alone. The shared **Configuration Check** panel carries only the global checks; each scraper's **target-configuration health** (a `Config` row: `N items loaded` / `M misconfigured` / `Failed`) is surfaced per-scraper, at the top of that scraper's **Service Status** panel alongside its settings section — built by the shared `config_check.config_view`/`add_config_row` (the interactive run shows the same `Config` row atop each **Scraping** panel). It footnotes per-scraper **settings issues** — a live timer whose schedule has drifted from the configured `execution_interval` (pointing at `./scrooge-alert schedule`) and an out-of-range `log_retention_days` — and surfaces **orphaned units** — installed `*-scraper.{timer,service}` units whose plugin is no longer registered (removed/renamed upstream) — each in its own red panel with the `./scrooge-alert uninstall --<plugin>` command to remove them, since they never run and are otherwise invisible to the per-plugin status loop.
- **Uninstallation:** Execute `./scrooge-alert uninstall` for a full teardown or pass `--<plugin>` to remove only that target's units while preserving the venv and other plugins.
- **Exit Codes:** The script utilizes specific exit codes to indicate failure states when running as a service (these can be easily viewed using the `status` command):
  - **`1`**: Indicates an unexpected application failure; inspect `logs/errors.txt`.
  - **`15`**: Indicates an issue with a target's tracked-items configuration, e.g. `config/skroutz.json` (file missing, wrong permissions, invalid JSON, or an invalid schema). Such a scraper is **skipped individually** — other selected scrapers still run or are provisioned — and the command finishes with this code if any target's config failed to load. For install/schedule/update, the failed target's existing units are left unchanged.
  - **`16`**: Indicates unusable notification configuration in `config/general.json`.
  - **`17`**: Indicates the scraper was blocked by the server due to rate limits.
  - **`18`**: Indicates that a parser or unexpected scraper fault exhausted all retries. Modeled remote/server errors remain successful and surface through error/stale notifications.
  - **`19`**: Indicates that machine state or its cooperative lock could not be loaded, persisted, or used safely.
  - **`20`**: Indicates that at least one configured notification failed to deliver. The `status` command presents this as a yellow notification warning; scraping continues.
  - **`21`**: Indicates that a selected scraper could not start because its private plugin dependencies are missing.
  - **`42`**: Indicates that every selected scraper target did not start because another instance of it is already running (file lock timeout). Background runs are single-target (systemd invokes one scraper per timer), so a lock skip there is by definition the whole run and always surfaces this code. In a manual multi-target run, a target that is skipped while others succeed does not raise it, since an otherwise successful run must not report a failure.
  - **`130`**: Indicates that the script was interrupted (e.g., via Ctrl+C or system termination).

## Engineering Decision Principles

Agents must optimize for long-term clarity, separation of concerns, testability, and maintainability. Architectural patterns are tools, not goals.

- Implement the smallest coherent change that fully solves the demonstrated problem. Do not add speculative extension points, generalized frameworks, or abstractions for hypothetical future requirements.
- Before changing code, identify which layer owns the behavior. Keep application policy, infrastructure I/O, persistence, presentation, and plugin responsibilities separate. Do not move behavior into a layer merely because it is convenient to access there.
- Preserve dependency direction. Infrastructure must not depend on application or TUI code; presentation must receive collected data rather than perform filesystem, configuration, network, or systemd access; plugins must use only their documented framework-facing contracts.
- Centralize rules and invariants that must remain consistent, such as error classification, status priority, schema validation, and persistence safety. Do not centralize unrelated code merely because it looks similar.
- Apply DRY to knowledge and policy, not every repeated expression. Small local duplication is preferable to a shared abstraction that couples unrelated responsibilities or makes behavior harder to understand.
- Introduce an abstraction only when it provides a concrete benefit: removing repeated policy, enforcing an invariant, isolating an external dependency, or creating a stable test seam. The benefit must outweigh the added indirection, API surface, and cognitive cost.
- Prefer explicit typed contracts and straightforward control flow over dynamic registries, implicit conventions, inheritance hierarchies, or metaprogramming when a simpler design provides the same safety.
- Design for local reasoning. A maintainer should be able to understand a behavior by reading its owning module and direct contracts without tracing unrelated layers or hidden global state.
- Keep plugin contributions additive and framework-light. Adding a normal plugin must not require changes to application orchestration, persistence, exit-status handling, shell scripts, or presentation code.
- Add dependency injection only at meaningful nondeterministic or external boundaries, such as clocks, clients, locks, storage, notifications, and process services. Do not add test-only production hooks or inject ordinary pure logic without a concrete need.
- Test behavior and boundaries rather than implementation details. Cover ownership decisions, failure classification, invariants, and externally visible results. Avoid mocks that merely reproduce the implementation.
- Consider failure modes and cleanup paths before implementation. New behavior must preserve resource cleanup, atomicity, malformed-data protection, lock safety, interruption behavior, and diagnostic usefulness where applicable.
- Do not broaden a change into an unrelated cleanup. Refactor adjacent code only when it is necessary to implement the requested behavior safely or removes a concrete maintainability problem exposed by the change.
- If a proposed change adds more coupling, indirection, maintenance burden, or failure modes than the problem justifies, reject it and explain why. Leaving clear, working code unchanged is an acceptable and often preferable outcome.
- When multiple designs are viable, prefer the one with fewer concepts, clearer ownership, smaller public surface area, and stronger focused tests. Record any non-obvious tradeoff in code comments or documentation close to the decision.

## Commit Message Guidance

Agents must never create commits, but when asked to suggest a commit message they must first inspect recent project history and match its established style and detail level.

- Use a concise conventional subject when consistent with recent history, such as `fix(locking): ...`, `refactor(errors): ...`, or `test(ui): ...`.
- Describe the outcome in the subject, not the activity. Prefer “classify lock storage failures as storage errors” over “update locking code.”
- Use left-aligned `-` bullets in the body with no leading indentation.
- Make the message understandable without reading the diff. It should preserve enough context for a future maintainer to understand what changed, why it changed, which architectural boundary owns it, and which important behavior was deliberately preserved.
- Explain the reasoning behind non-obvious decisions. Include why a shared policy, typed contract, or boundary was introduced and why responsibilities remain in separate layers.
- Describe important invariants and compatibility decisions, such as unchanged plugin responsibilities, preserved persistence safety, contention semantics, or presentation behavior.
- Prefer behavior-level details over file inventories, symbol lists, or a chronological account of implementation steps.
- Avoid filler, repetition, promotional language, and vague phrases such as "improve robustness," "clean up code," or "various fixes" unless the message immediately states the concrete behavior involved.
- Give each bullet one clear purpose. Combine closely related implementation and rationale, but do not repeat the subject or restate another bullet.
- Mention tests and the mandatory local CI gate only when they were actually run. Include the exact passing test count when known, and never claim CI readiness when the required gate failed or could not run.
- Keep the message detailed enough to preserve history and design intent, but no longer than necessary to explain the change accurately.

## Development Conventions
- **Scraping Practices & Rate Limiting:** The framework intentionally paces requests using a base delay (20s) plus randomized jitter (1-5s) between item checks to reduce pressure on monitored sites. The delay separates consecutive requests only: a target's first request of a run starts immediately, since runs are already spread out by the timer's `RandomizedDelaySec`. Retry backoff is unaffected. Concurrency is avoided. Do not "optimize" this away.
- **Data Integrity:** Runtime never writes `config/*.json`. Scraper machine updates go through `JsonStateRepository` under the existing per-target lock; reminder updates go through `ReminderStateRepository` under the reminder lock. Both use the atomic writer and preserve malformed existing state.
- **Managed-path symlink policy:** Scrooge Alert creates a real root `venv/` directory and regular canonical systemd unit files. The enablement symlinks that systemd creates below directories such as `timers.target.wants/` are expected systemd-owned entries, not project-managed destinations. Symlinks placed at project-managed destinations are unsupported: mutating commands reject them before changing packages, units, or timer state, while teardown remains link-aware so uninstall can remove a unit entry without following its target. JSON migration inputs must likewise be regular files because migration replaces them atomically. Keep these small fail-closed boundary checks, but do not add symlink normalization, target-following writes, or exact-representation preservation behavior.
- **Error Handling & Logging:** When running silently in the background, exceptions are caught and logged to the relevant `errors.txt` — `logs/<target>/errors.txt` for a specific scraper (e.g. `logs/skroutz/errors.txt`), falling back to the root `logs/errors.txt` for top-level crashes with no target context. Background stdout is written to `logs/<target>/output.log`, which rotates daily at midnight UTC and keeps the scraper's configured `log_retention_days` of files (default 7; the surplus is pruned at the next rotation). Timestamps in these logs are recorded in UTC. If critical errors occur (like repeated scraping failures or a total crash), the script utilizes the Apprise notifier to alert the user of the failure.
- **Code Style:** Adding a store is additive: use `./scripts/dev/plugin-create.sh` and change only the new source and test packages. Targets and declaration keys are snake_case; domains are normalized hostnames/IPs only and may overlap across adapters. Export conventional `Client`, declare a parsed-URL predicate and canonical interval, and add only optional custom fields/settings/dependencies. Compilation validates codecs, already-canonical defaults, reserved keys, control-character safety, URL matcher behavior, and runtime Python files; the contributor verifier owns documentation, tests, examples, package isolation, and import-effect checks. Runtime results validate nonblank currency/title, finite non-negative non-boolean prices, immutable snapshotted offers, and absolute HTTP(S) offer URLs. Invalid construction follows parse retries and never persists or alerts.
