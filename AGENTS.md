# Scrooge Alert - Development Context

## Project Overview
This project is an automated Python application designed to monitor product prices across supported stores — Skroutz product pages and insomnia.gr classifieds listings — and send push notifications when prices drop below user-defined target thresholds. 

- **Main Technologies:** Python 3, `apprise` (for versatile push notifications via Telegram, Discord, etc.), `tls_client` (for evasive web scraping by mimicking browser TLS fingerprints), and systemd (for automated background scheduling on Linux).
- **Architecture:** The application features a modular, plugin-based architecture residing in `src/core/`. The entrypoint is `main.py`, which delegates to specialized modules:
  - **Scrapers (`scrapers/`)**: Self-contained plugin packages grouped by target store. Each package contains its client, model, storage, package-local `config.example.json`, an optional colocated `requirements.txt`, local documentation, and an import-light `plugin.py` exporting a declarative `PLUGIN`. The package directory supplies the target/config name; `PluginDefinition` supplies display name, frozen host-only domains, lazy `ClassRef` bindings, canonical default interval, and custom setting specs. The framework owns all systemd directives. **Import-light contract (load-bearing):** `plugin.py` and the package `__init__` are imported for every plugin during discovery, so they import only stdlib + base contracts — never a transport/parsing library (`tls_client`, `selenium`, ...). The registry resolves class references only on first instantiation.
    - **Base Contracts (`scrapers/base/`)**: `BaseScraperClient.scrape(item)` consumes the fully parsed tracked row and returns either `PriceResult` for a product page or `ListingResult` for a listing/search. A listing result carries an immutable tuple of independent `OfferMatch` values; an empty tuple means "checked fine, no offer matched," so the orchestrator refreshes `last_checked` without touching `last_price`. `BaseTrackedItem.identity_key()` is the single stable identity used for deduplication, update caching, and save merging; plugins with multiple logical rows per URL include their distinguishing model fields there. Extra fields compose through `parse_extra_fields`, with no virtual URLs or paired storage hooks. The generic `SettingSpec`/`ResolvedSettings` engine lives in neutral `core/settings/`; the registry automatically prepends scraper framework specs to the custom specs declared by a plugin. Canonical-key → systemd-`OnCalendar` translation lives at the registry schedule boundary.
    - **Registry (`scrapers/registry.py`)**: A unified `ScraperRegistry` handles URL-to-plugin resolution, lazy client/manager instantiation, auto-discovery via `pkgutil`, immutable normalized runtime records, and the single validation gate for descriptor/domain conflicts. It passes each target's resolved settings to its client/manager at construction. The import-light `resolve_all_settings`, `resolve_value`, and `resolve_schedule` helpers read config preferences and compute framework-owned schedules without loading a plugin's storage stack; the stable `core.scrapers.cli` command is the sole Python bridge used by POSIX management scripts.
  - **Orchestration (`orchestrator.py`)**: `ScrapingOrchestrator` runs a store-agnostic execution loop over targets and products, handling per-target file locks (`locks.py`), retries, and notification dispatch. For a listing-type result it sends one price-drop push per matching advert below target (each linking to that advert); a no-match result (`price=None`) refreshes the row's timestamp without alerting.
  - **Preflight loading (`preflight.py`)**: `TargetLoad` and `load_targets` — the run's single storage read/validation phase (file I/O + registry cache-warming). Lives outside `ui/` because it is orchestration-side work; the UI only renders its outcomes (the per-scraper `Config` row). The mode-specific gating/rendering entry point named `preflight()` remains in `ui/config_check.py`, since its interactive half draws the Configuration Check panel.
  - **Notifications (`notifier.py`)**: Apprise wrapper; used both for price-drop alerts and to notify the user of critical failures.
  - **Configuration & Validation (`constants.py`, `utils.py`)**: Centralized constants and environment/file health checks.
  - **Terminal UI (`ui/`)**: The presentation package holding everything drawn to the terminal — the shared `StatusPanelBuilder` primitive (`ui/panel.py`), the Configuration Check panel and shared row helpers (`ui/config_check.py`), and the live interactive Scraping panel (`ui/tui.py`), which manages the progress bar during sleep intervals using the Strategy pattern (`ExecutionStrategy`): `InteractiveExecutionStrategy` renders the Rich progress bar; `SilentExecutionStrategy` is used with `--quiet` (and by the systemd service).
  - **CLI Tools (`ping.py`, `status.py`)**: Dedicated scripts for specific CLI commands to maintain separation of concerns.
  User configuration is completely externalized to `.env` (`NOTIFICATION_URLS`, comma-separated Apprise URLs), one derived `config/<target>.json` per scraper, and an optional project-wide `config/general.json` (a user-authored `settings` block — currently the periodic liveness `reminder` and its schedule — resolved through the same settings engine, alongside machine-written state such as `last_reminder`). A scraper config holds an optional top-level `settings` object alongside its tracked rows. The JSON config also doubles as state: the scraper writes the latest price and check timestamp (stored in UTC) back onto item rows via `update_item`. The `settings` block is read-only user input; machine-owned runtime state lives on item rows. Settings are read at config/schedule time through registry helpers and at scrape time through the `self.settings` accessor injected into each plugin's client and manager.

## Building and Running
The application is primarily intended for automated background execution but provides wrapper scripts for easy management and manual testing. All execution goes through the venv (`./venv/bin/python3`); the wrapper scripts handle this for you.

A test suite lives under `tests/` (`tests/unit/`, `tests/integration/`, the terminal-UI snapshot suite in `tests/ui/`, and `tests/shell/` — pytest-driven `sh` subprocess tests for the pure logic in `scripts/lib/common.sh`). It runs under **pytest**, configured in the repo-root `pyproject.toml` (which puts `src` — the `core` package root — and `tests` on `sys.path`, so tests need no `PYTHONPATH=` prefix). Install the toolchain with `pip install -r requirements-dev.txt` and run the whole suite with `./venv/bin/python3 -m pytest`. CI (`.github/workflows/tests.yml`) runs it on Python 3.10 through 3.14 for every push and pull request, plus **shellcheck** over every shell script and `basedpyright src` for production static contracts. Typing uses the `[tool.pyright]` section in `pyproject.toml`: `pythonVersion = "3.10"`, `typeCheckingMode = "standard"`, and `extraPaths` mirroring pytest's import roots. The codebase uses Python 3.10+ syntax exclusively — PEP 604 unions (`X | None`) and PEP 585 builtin generics (`list[str]`); abstract collections come from `collections.abc`. Shared test infrastructure lives in `tests/support.py`: autospec'd mock factories for the orchestrator's collaborators, the declarative `fake_plugin(...)` fixture factory, and `registry_sandbox(*plugins)` for isolated registry state. **User-facing run wording lives in `core/messages.py`**: production and tests share the same phrases, and UI changes regenerate with `UPDATE_SNAPSHOTS=1`. `tests/integration/test_plugin_contract.py` is a per-plugin battery over `registered_targets()` (package-local example exists/loads/round-trips, URLs route back, lazy client resolves), so a new store gets it with zero new generic test files. `tests/integration/test_e2e_core_loop.py` drives the real orchestrator and `main()` against a stdlib fake store; the `E2E_RUN` snapshot surface captures the real interactive panel — see `tests/ui/README.md`.

- **Installation:** Execute `./install.sh`. This creates the venv, installs core dependencies plus each selected plugin's registry-computed colocated `requirements.txt`, and generates one systemd user timer+service pair per plugin. The effective cadence is the valid `settings.execution_interval` or the plugin definition's canonical `default_interval`. The framework exclusively renders `OnCalendar`, explicit `Unit=<plugin>-scraper.service`, `RandomizedDelaySec=180s`, and `Persistent=true`; plugins cannot inject timer directives. A missing private dependency fails that target with actionable `PluginDependencyError` guidance.
- **Automated Execution:** Handled automatically by the per-plugin systemd timers (`<plugin>-scraper.timer`, e.g. `skroutz-scraper.timer`).
- **Service Management:** Use `./scripts/disable.sh` to temporarily stop and disable the background timer(s), `./scripts/enable.sh` to resume them, and `./scripts/stop.sh` to forcefully kill a running execution. With no flag these act on **all** plugins; pass `--<plugin>` (e.g. `./scripts/disable.sh --skroutz`) to target a single store. `./scripts/schedule.sh` re-applies each scraper's configured `execution_interval` to its installed timer (atomically rewrites the timer, then `daemon-reload`; an active timer is restarted and verified); run it after editing that setting — a missing config or an unsupported value is reported and that timer left unchanged. Systemd queries/actions fail closed: only known absent/inactive states are benign, every action verifies its postcondition, multi-target commands report all independent failures, and update/uninstall perform no destructive phase unless every scraper was safely stopped. The teardown commands (`disable`/`stop`/`uninstall`) validate a targeted `--<plugin>` against the **union of registered plugins and installed units** (`is_known_target` in `common.sh`), so they can still tear down a *leftover unit of a plugin removed upstream* while rejecting a genuine typo; `install`/`enable`, by contrast, require the plugin to exist in the registry (they need code to run, not just a unit to remove). `./update.sh` (repo root) updates the installation; it derives which plugins to reprovision from the units already installed (globbed via `list_installed_plugins`), so it **preserves the user's original selection** — a single-plugin install stays single, and a store newly added in the pulled version is *not* auto-provisioned (and its dependencies not installed) until an explicit `./install.sh --<store>`. A plugin that was removed/renamed in the new version is skipped rather than aborting the update. With nothing installed, update falls back to a full install. All shell scripts are POSIX `sh` (verified against `dash`, shellcheck-checked in CI) and source shared helpers from `scripts/lib/common.sh` (colors, plugin enumeration via the registry, verified systemd lifecycle actions, atomic unit rendering, `list_supported_intervals`, and `registry_diagnose`), so adding a new store requires no changes to any existing script.
- **Manual Execution:** Execute `./scripts/run.sh` to run the scraper interactively and view output logs in the terminal. Flags: `--quiet` (no console output) and one dynamically generated flag per registered plugin (e.g. `--skroutz`) to run only that scraper. The `--ping` and `--status` flags must be used alone.
- **Direct Invocation:** `./venv/bin/python3 src/core/main.py` — the entry scripts (`main.py`, `status.py`, `ping.py`) insert `src/` (the parent of the `core` package) into `sys.path`, and all intra-project imports are absolute from that package (e.g. `from core.scrapers.registry import ...`), never implicitly relative (`from scrapers...`) or rooted at `src` (`from src.core...`).
- **Help Message:** Execute `./scripts/run.sh --help` to print the help message and view all available script arguments.
- **Testing Notifications:** Run `./scripts/run.sh --ping` to send a test payload and verify that the Apprise URLs in your `.env` file are configured correctly.
- **Health Checks:** Run `./scripts/run.sh --status` to perform a comprehensive health check. This validates the configuration (products and notification settings), checks for available script updates, and verifies the status of the background systemd service and timer. The shared **Configuration Check** panel now carries only the **global** checks (software version + `.env`); each scraper's **products-config health** (a `Config` row: `N items loaded` / `M misconfigured` / `Failed`) is surfaced per-scraper, at the top of that scraper's **Service Status** panel alongside its settings section — built by the shared `config_check.config_view`/`add_config_row` (the interactive run shows the same `Config` row atop each **Scraping** panel). It footnotes per-scraper **settings issues** — a live timer whose schedule has drifted from the configured `execution_interval` (pointing at `./scripts/schedule.sh`) and an out-of-range `log_retention_days` — and surfaces **orphaned units** — installed `*-scraper.{timer,service}` units whose plugin is no longer registered (removed/renamed upstream) — each in its own red panel with the `./scripts/uninstall.sh --<plugin>` command to remove them, since they never run and are otherwise invisible to the per-plugin status loop.
- **Uninstallation:** Execute `./scripts/uninstall.sh` to cleanly stop and disable the systemd services and remove the virtual environment (user data is preserved). It removes every installed `*-scraper.{service,timer}` unit (robust to plugins deleted from the source tree). Pass `--<plugin>` (e.g. `./scripts/uninstall.sh --skroutz`) to drop only that plugin's units while keeping the venv and other plugins.
- **Exit Codes:** The script utilizes specific exit codes to indicate failure states when running as a service (these can be easily viewed using the `--status` flag):
  - **`15`**: Indicates an issue with a plugin's products config file, e.g. `config/skroutz.json` (file missing, wrong permissions, or invalid JSON). Such a scraper is **skipped individually** (its failure surfaced as its `Config` row) — the other scrapers still run — and the run finishes with this code if any target's config failed to load. Since each systemd service runs a single plugin, a background run is effectively single-target, so this reproduces the prior behavior there.
  - **`16`**: Indicates an issue with the `.env` file configuration.
  - **`17`**: Indicates the scraper was blocked by the server due to rate limits.
  - **`18`**: Indicates that a parser or unexpected scraper fault exhausted all retries. Modeled remote/server errors remain successful and surface through error/stale notifications.
  - **`19`**: Indicates that scraped state could not be persisted through the atomic config save path.
  - **`20`**: Indicates that at least one configured notification failed to deliver. `--status` presents this as a yellow notification warning; scraping continues.
  - **`21`**: Indicates that a selected scraper could not start because its private plugin dependencies are missing.
  - **`42`**: Indicates that a specific scraper target did not start because another instance of it is already running (file lock timeout).
  - **`130`**: Indicates that the script was interrupted (e.g., via Ctrl+C or system termination).

## Development Conventions
- **Scraping Practices & Rate Limiting:** The scraper intentionally paces requests using a base delay (20s) plus randomized jitter (1-5s) between product checks to avoid triggering Skroutz's anti-bot protections. Concurrency is avoided to maintain a low profile. Do not "optimize" this away.
- **Data Integrity:** Updates to the `config/*.json` files (such as logging the latest price and check timestamp) must go through the existing atomic save mechanism to prevent file corruption in case of unexpected interruptions.
- **Error Handling & Logging:** When running silently in the background, exceptions are caught and logged to the relevant `errors.txt` — `logs/<target>/errors.txt` for a specific scraper (e.g. `logs/skroutz/errors.txt`), falling back to the root `logs/errors.txt` for top-level crashes with no target context. Background stdout is written to `logs/<target>/output.log`, which rotates daily at midnight UTC and keeps the scraper's configured `log_retention_days` of files (default 7; the surplus is pruned at the next rotation). Timestamps in these logs are recorded in UTC. If critical errors occur (like repeated scraping failures or a total crash), the script utilizes the Apprise notifier to alert the user of the failure.
- **Code Style:** Adding a store is additive: create one new package without editing existing framework files. Plugin targets are safe unique identifiers; derived config filenames cannot collide with `general.json`; domains are normalized hostnames/IPs only with no schemes, paths, credentials, or ports. Declare a canonical `default_interval`, custom settings only, and colocated private dependencies. Registration validates metadata, setting callables/default displays, class references, and domain conflicts. Runtime results require a nonblank currency, dictionary metadata, finite non-negative non-boolean prices, and—on listing results—an immutable tuple of valid `OfferMatch` values with absolute HTTP(S) URLs. Invalid results retry as parse failures and never persist state or send price-drop alerts. Listing stores put logical row identity on their item model and pass that item directly to the client.
